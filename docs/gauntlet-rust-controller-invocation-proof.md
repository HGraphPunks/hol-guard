# Provider status and controller invocation parity

The Python v1 `verify_provider_status` function validates an externally pinned MLX adapter and an idle provider-quota snapshot before a controller treats provider counters as known usage. The Rust `verify_provider_status` function matches two accepted Python snapshots and sixteen refusals, including wrong adapter and binding pins, halted or pending usage, forged journal identity, boolean integer fields and inconsistent remaining budget. It returns the quota status as accounting data only; it does not grant model admission.

The Python `audit_invocations` function examines retained shard invocation directories and compares provider before/after counters with the controller ledger and aggregate token charge. The Rust `audit_controller_invocations` function accepts already-read immutable file bytes and outside config, manifest and provider pins. It checks exact retained file hashes, preflight binding, shard index, provider status and nonnegative before/after and ledger deltas. Its output always includes `qualification_eligible: false`. Fourteen Python-frozen cases cover absent/empty directories, preflight failure, a valid delta, aggregate mismatch, changed source pins or files, halted and decreasing provider counters, a wrong ledger delta and incomplete invocation files.

The fixture generator relaxes Python's Linux Root state-directory check only for its own disposable synthetic directory. It leaves production readers unchanged.

These functions still lack a Root-owned, descriptor-relative reader of retained invocation directories, a binding to independently audited shard ledgers and a cryptographic or external anchor for the provider snapshots. The Python invocation receipts are local-integrity records, not signed attestations. Until those boundaries and the live execution path are proven, they remain diagnostic Rust parity functions and cannot turn any result green.
