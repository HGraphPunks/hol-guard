# Worker-owned deterministic controller key: isolated handoff proof

The migration now has an opt-in handoff for a Rust-owned deterministic run. On Linux ARM, the internal Rust worker generates a fresh Ed25519 seed with `ring::SystemRandom`, writes it to a 32-byte Root-owned memfd, sets all four write/shrink/grow/seal seals, and keeps `FD_CLOEXEC` set in the parent. Under the existing exclusive worker lease, it first consumes the one-use job ID with a v2 started marker containing the public key, then writes an exclusive 0600 canonical `*.controller-key.json` sidecar bound to that exact job/source/deployment/worker-generation/started-marker digest and public key. The fixed `execveat` child clears `FD_CLOEXEC` for that descriptor only and receives its number through the exact additional environment key `HOL_GAUNTLET_RUST_SIGNING_KEY_FD`. The parent rechecks the marker and sidecar before returning from launch and after child cleanup; an orphan key sidecar blocks another reservation. Existing v1 markers remain readable and are never treated as keyed runs.

The Python adapter accepts that descriptor only for the deterministic profile on Linux as Root. It requires a decimal descriptor in the fixed range, a Root-owned unlinked regular file of exactly 32 bytes, all required seals and an offset of zero. It removes the environment selector, reads once, closes the descriptor, and supplies the resulting Ed25519 key to all six deterministic controls. With no descriptor, the existing Python execution path continues to create its own per-control key. The adapter is pinned at SHA-256 `ff3ece762f411439385fff86cc9ac017203f93a0ba0e4e63bae16ceceae2529b` (`ci_pipeline.py`), `e819cf846a62506a3b3523f4b6471d3fb5f85c117578fafc5a1746ef925b06ae` (`deterministic.py`) and `138160dc6daa77d1fed591f73cab240b0f3824529dcbb337f7ebb8bce6fc4777` (`deterministic_control.py`). The Rust key module is SHA-256 `9c44027ba334350a903ea3b3f1ea8d218e107dffdd6fd53f41d5aa1bfaf42eff` at this proof.

On the pinned ARM64 Rust 1.88.0 container, the key test passed: a sealed descriptor stayed closed across an ordinary exec, survived an explicit inert child handoff, and produced the expected public key from the child-read seed. A restarted journal read the same public pin; a duplicate pin, wrong started-marker hash, changed sidecar public key and stale key sidecar were refused. A v1 marker cannot be retroactively keyed. The worker package passed 29 unit tests and 19 integration tests with three pre-existing host-cgroup observation tests excluded because the Docker cgroup path does not match the VM's systemd path. Warnings-denied Clippy and formatting passed. The updated 426-file source inventory test passed using the worktree index in the same pinned ARM64 container. The Python adapter and deterministic forwarding tests passed 94/94 under Root in a pinned Linux ARM Python 3.12 container and 93 passed/one Linux-only skipped on macOS. These are isolated tests, not a Rust-controlled benchmark run.

The complete outside-key exit remains open. No reviewed source-matched controller/private-cell install has run this new path on the VM. The host must retain the v2 started-marker hash independently before controller execution, bind it and the sidecar digest into terminal evidence, and refuse a changed marker or sidecar after crash/restart. Without that outside hash, a Root replacement cannot be distinguished merely by rereading local files. The signed control records, SDK/Native peers, kernel observations and physical effects are not independently scored. The worker is unwired, all Rust observations remain `execution_eligible: false`, and the PR gate remains passive. The changed Python bytes alter the controller-tree and private-cell source-map digests, so the retained VM artifacts cannot qualify a fresh run until rebuilt and independently pinned.
