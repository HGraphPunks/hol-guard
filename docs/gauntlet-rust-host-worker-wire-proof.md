# Rust host/VM wire proof (2026-10-20)

This proof advances two separate boundaries on draft PR #5402. It does **not** run a benchmark or make a worker eligible to qualify a build.

The macOS host crate now owns a caller-launched child during the prepared/ack exchange. `HostControllerKeyPinJournal::accept_prepared_child` reads at most one 1-KiB prepared frame, checks the planned source/job/deployment/generation tuple, fsyncs the one-use host key record, and only then writes the acknowledgement. A refusal kills and asynchronously reaps the host child. It reports whether a pin exists or is uncertain; an acknowledged job remains consumed even if the host transport later times out. `HostPreparedProcess::wait_bounded` bounds only the host process and never claims that killing `limactl` stopped a guest descendant. This adapter still requires an independently reviewed Lima executable, VM, guest worker, controller source and deployment before a live dispatch.

The host also has `VmRustShadowPlan`, which freezes a read-only `progress` request and derives the sole guest executable path from a 64-hex outside binary hash. It binds one canonical response to the request, outside worker-generation pin and deployment pin. It refuses extra stdout, malformed frames, wrong identity and failed transport. The plan explicitly reports `binary_pin_verified: false` and `execution_eligible: false`; a path containing a hash is not executable attestation. `gauntlet-host-shadow-rust-worker` is a local diagnostic for this plan and never selects `run`.

On native ARM64 Docker, `cargo test --locked -p gauntlet-host-state` passed the full host crate, including three new child-process tests and three fixed-Lima-plan tests. `cargo clippy --locked -p gauntlet-host-state --all-targets -- -D warnings` and workspace format checks passed. The earlier pushed documentation head `df0034b9` completed repository product CI [run 39552093120](https://github.com/hashgraph-online/hol-guard/actions/runs/39552093120) successfully and all three isolated Rust checks passed; this new source still requires its own pushed-head CI.

A release-mode Linux ARM64 `gauntlet-vm-worker-shadow` built from the current draft source weighed 906,392 bytes and had SHA-256 `2fd5fec1792642ba43435dc38aa007daccf28f1cdb04f5e30a5e9ffcf8c51821` in the build container, on the Mac transfer copy, and in the VM. It was installed in a separate Root-owned 0755 file at `/opt/hol-gauntlet/rust-worker-shadow-2fd5fec1792642ba43435dc38aa007daccf28f1cdb04f5e30a5e9ffcf8c51821`; the independent Rust worker journal remained Root-owned 0700 at `/var/lib/hol-gauntlet-rust/worker-state`. Temporary transfer copies were removed after verification. The current Python observer and controller were untouched.

Through `limactl shell hol-beta-bootstrap-20261016-004 -- sudo -n` and that exact binary, a synthetic source (`a` repeated 40), job `0123456789abcdef`, deployment (`b` repeated 64) and generation (`c` repeated 64) received a canonical `hol-gauntlet-worker-response.v1` with `state: not-started`, exit 0 and empty stderr. The same request without `sudo` returned exit 2 and `Linux Root-owned private worker directory required`. No `0123456789abcdef.started.json` appeared. VM free disk after install was 14,887,391,232 bytes, above its configured 8-GiB floor. This is a read-only protocol/VM connection observation against synthetic pins, not a Rust-controlled Guard result.

The next live execution step must authenticate the exact host and guest binaries and Root controller generation from a reviewed base, bind a fresh deployment and source archive to a one-time worker lease, carry the prepared/ack exchange over that attested Lima child, run the controller in the job cgroup and product slice, and authenticate its terminal report and six controls before any verdict. An interruption after acknowledgement must remain unknown until independent guest reconciliation. The model-backed campaign and provider accounting exits remain separate in the [execution checklist](gauntlet-rust-execution-checklist.md).
